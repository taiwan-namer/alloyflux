# AI 監工：產品規格（M1 詳細、M2～M3 整體）

> 狀態：草案，待發起人確認。本文件只是規格，尚未動任何程式。
> 價格查證日期：2026-11-25（OpenAI 官方價目、Vercel Sandbox 官方價目、E2B 官方價目）。

## 0. 一句話定位

**「交代目標和期限，AI 自己規劃、自己施工，高階模型全程監工；你只看進度、批准關鍵動作。」**

給不太懂程式的老闆或 PM 使用：他看得懂進度、費用、風險，不需要看程式碼，也不需要在中間轉手。

## 1. 核心承諾（對使用者）

| 承諾 | 怎麼做到 |
|---|---|
| 不用等來等去 | 平台自己推進每一步；人只在「開工確認、批准不可逆動作、最後驗收」三個時間點出現 |
| 不會跑掉 | 主線帳本（工期表）＋範圍外指令自動暫扣＋退回 2 次由監工決定縮小、換做法或暫停 |
| 不會亂改正式環境 | 只寫工作分支；合併到 main、部署、正式資料庫操作一律要人點頭 |
| 花多少錢看得到 | 每個工作包顯示預估與實際花費；整個專案有預算上限，快到就停下來問 |

## 2. 使用流程與畫面

### 2.1 開專案（約 2 分鐘）

1. **連接 GitHub**：一鍵授權（GitHub App，只授權選定的 repo）。
2. **說明目標**：白話描述，例如「左側會議室讀取太慢，要 1 秒內」；可附截圖。
3. **設定期限與預算**：例如「3 天內、上限 30 美元」。
4. 按「請監工評估」。

### 2.2 工期表（M1 的核心畫面）

監工讀完 repo 後產出，畫面以白話為主，技術細節預設收合：

```
專案：會議室效能改善                     預估 2.5 天｜預估費用 US$12～18｜風險：中
──────────────────────────────────────────────────────
① 找出左側清單慢的原因          0.5 天  US$2   ⬜ 待開工
   驗收：量到的載入時間＋原因證據
② 改成分頁載入                  1 天    US$6   ⬜ 待開工
   驗收：100 個會議室時 < 1 秒（自動計時）
③ 回歸測試與上線前檢查          0.5 天  US$3   ⬜ 待開工
   驗收：既有測試全過；需要你批准部署
──────────────────────────────────────────────────────
監工備註：目前每次開頁都把全部會議室和訊息數一次撈出（lib/xxx.ts:120）。   [展開技術細節]
                                               [修改計畫]  [開工]
```

每個工作包都有：白話標題、預估工時、預估費用、驗收標準（可量測）、目前狀態。
「展開技術細節」才會看到檔案位置、程式片段、監工的推理依據。

### 2.3 施工中（M2～M3）

- 進度看板：每個工作包的狀態（⬜ 待開工／🟡 施工中／🔍 監工驗收中／✅ 通過／⏸ 暫停／⛔ 需要你決定）。
- 每個工作包可點開：做了什麼（白話）、測試結果、監工評語、花費。
- 側邊欄「跟監工對話」：隨時問進度、改方向（沿用現在的會議室對話）。

### 2.4 收尾

- 每個通過的工作包開一個 GitHub PR，內文含監工驗收紀錄與證據。
- 使用者按「合併」；部署另外再按一次確認。
- 通知只在三種情況發：需要你批准、需要你決定（僵局）、全部完成。

## 3. 角色分工

| 角色 | 由誰 | 做什麼 | 不做什麼 |
|---|---|---|---|
| 監工 | 最高模型（例：gpt-6.2-astra） | 讀 repo 規劃、訂驗收標準、看差異與測試結果驗收、處理僵局 | 不自己大量寫程式 |
| 施工 | 便宜模型（例：gpt-6.1-terra 或 gpt-6.2-sol） | 在雲端環境裡寫程式、跑測試、修到測試過 | 不決定範圍、不碰 main |
| 證據 | 程式自動產生 | 測試輸出、分支差異、計時數字 | 不經任何模型轉述 |
| 人 | 使用者 | 確認工期表、批准不可逆動作、驗收 | 不需要轉手訊息 |

## 4. M1：連 GitHub＋監工讀 repo＋產出工期表（詳細規格）

### 4.1 範圍

做：

- GitHub App 一鍵連接，專案綁定一個 repo 與基準分支。
- 監工的「工具迴圈」：模型可以邊想邊呼叫唯讀工具，直到產出工期表。
- 工期表畫面（2.2）：可修改、可確認開工（M1 的「開工」先只是鎖定計畫）。
- 每回合花費記錄與顯示。

不做（留給 M2）：雲端施工、開 PR、自動測試。

### 4.2 監工可用的唯讀工具（全部走 GitHub API，不需要使用者裝任何東西）

| 工具 | 用途 | 上限 |
|---|---|---|
| `list_dir(path)` | 看資料夾結構 | 每次 ≤ 300 項 |
| `read_file(path, startLine, endLine)` | 讀指定行 | 每次 ≤ 400 行 |
| `search_code(query, pathGlob?)` | 找符號或字串 | 每次 ≤ 30 筆 |
| `recent_commits(path?)` | 看最近改了什麼 | ≤ 20 筆 |
| `compare(base, head)` | 看兩個版本的差異 | ≤ 2,000 行 |

每個回合工具呼叫總數上限（建議 40 次）與讀取總量上限（建議 6 萬字），超過就強制收斂產出結論。

### 4.3 工具迴圈（平台端）

1. 送出：系統提示（固定，吃快取）＋專案目標＋工具定義。
2. 模型回「要呼叫工具」→ 平台執行（GitHub API）→ 結果附加在對話尾端 → 再送一次。
3. 重複直到模型輸出工期表 JSON，或撞到上限。
4. 因為每次都是在同一段對話尾端追加，前面的內容都吃得到快取（OpenAI 快取價為原價的 5%）。

需要改的程式：`lib/providers.ts` 的 OpenAI 通道加上 `tools` 與工具呼叫事件處理；`lib/gateway.ts` 加一層迴圈。現有一問一答的路徑不受影響。

### 4.4 工期表資料結構

沿用 `lib/strategy-ledger.ts` 的帳本與工作包，新增欄位：

- 工作包：`estimateDays`、`estimateUsd`、`acceptance[]`（必須可量測）、`riskLevel`、`plainSummary`（白話）、`techNotes`（技術細節，預設收合）。
- 專案：`deadline`、`budgetUsd`、`spentUsd`、`repo`、`baseBranch`。

### 4.5 安全

- GitHub App 權限：M1 只要「讀取程式碼」；M2 才加「寫入工作分支、開 PR」。
- main 分支建議設保護；平台程式碼層面也禁止寫 main。
- repo 內容只在回合中暫存，不長期保存原始碼；只保存監工引用的片段。

### 4.6 M1 驗收標準

1. 新使用者從連 GitHub 到看到工期表，操作步驟 ≤ 5 步、等待 ≤ 5 分鐘。
2. 拿本專案（alloyflux）跑「左側會議室讀取超久」：工期表指出的原因與檔案位置正確（由你或我人工核對）。
3. 每個工作包都有可量測的驗收標準。
4. 單次規劃花費 ≤ US$2（見第 7 節估算）。

### 4.7 M1 工作量

約等於今天完成的三個階段（帳本＋省 token＋automax）合計的 1.5 倍。

## 5. M2：單一工作包全自動施工（整體規格）

1. 使用者按「開工」→ 平台建立雲端執行環境（建議 Vercel Sandbox，平台本身就在 Vercel，同一帳單與 SDK）。
2. 環境內：clone repo → 建工作分支 → 施工模型實作 → 跑測試 → 修到過或撞上限。
   - 施工引擎建議直接用開源的 Codex CLI 無互動模式（以 API 金鑰＋便宜模型執行），不自己重寫寫程式的 agent。開工前會實測確認。
3. 平台自動收集證據：測試輸出、分支差異、計時數字。
4. 監工驗收：通過 → 開 PR；退回 → 附具體原因再施工；退回 2 次 → 監工決定縮小範圍、換做法或暫停（沿用帳本的僵局處置）。
5. 驗收標準：拿 alloyflux 的一個真實小工作包，從開工到開出 PR 全程無人介入。

工作量：約 M1 的 1～1.5 倍。

## 6. M3：多工作包無人值守＋看板＋通知＋預算（整體規格）

- 依工期表順序自動推進下一個工作包；有相依關係的等前一個合併。
- 進度看板（2.3）、白話週報／晨報。
- 通知：Email（之後可加 LINE），只在需要批准、需要決定、完成時發。
- 預算控管：每個工作包與整個專案都有上限；預估超支時先停下來問。
- 部署批准：合併後如需部署，由使用者在網頁按確認。

工作量：約 M1 的 1 倍。

## 7. 費用估算（每個工作包，含假設）

官方價格（每百萬 tokens，標準方案）：

| 模型 | 輸入 | 快取輸入 | 輸出 |
|---|---|---|---|
| gpt-6.2-astra（監工） | $8.00 | $0.40 | $40.00 |
| gpt-6.2-sol（施工，較強） | $2.00 | $0.10 | $10.00 |
| gpt-6.1-terra（施工，便宜） | $1.00 | $0.05 | $5.00 |

雲端環境：Vercel Sandbox 每 vCPU 小時 $0.128（只算實際用 CPU 的時間）＋每 GB 記憶體小時 $0.0212。

| 項目 | 假設 | 估計 |
|---|---|---|
| 監工規劃（每專案一次） | 新讀 3 萬＋快取 15 萬 tokens，輸出 8 千 | 約 US$0.6 |
| 監工驗收（每次） | 新讀 3.5 萬，輸出 3 千；平均 1.5 次 | 約 US$0.4～0.6 |
| 施工（每工作包） | 新讀 30 萬＋快取 150 萬，輸出 4 萬（gpt-6.2-sol） | 約 US$1.2（用 terra 約 US$0.6） |
| 雲端環境 | 2 vCPU、4 GB、20 分鐘 | < US$0.1 |
| **合計（每工作包）** | | **約 US$1.5～3** |

對照：在 Cursor 用最高模型，你目前改一次約扣 60 美元方案的 3～5%（約 US$1.8～3），一個工作包通常要改好幾次。
所以每個工作包的費用大約是同級或更低；真正的差別是：不用人在旁邊、證據可信、一路有監工。

以上是估算，M1 做完會用 alloyflux 實測並更新數字。

## 8. 與現有程式的對應

| 現有 | 在 AI 監工裡 |
|---|---|
| `lib/strategy-ledger.ts`（帳本、工作包、退回 2 次升級、暫扣不可逆指令） | 工期表與監工規則，直接沿用並擴充欄位 |
| 策略會議室對話 | 「跟監工對話」側邊欄 |
| /sources 的一鍵 OAuth 流程 | 一鍵連 GitHub 照同樣模式 |
| `lib/gateway.ts`、`lib/providers.ts` | 加上工具迴圈 |
| 每回合計費與 token 統計 | 工作包與專案的花費顯示、預算上限 |
| automax `cli.py`、Cursor 轉手 | 由雲端施工取代；保留給你自己內部使用 |
